# ABI-managed Privy workspace wallets

The user selected ABI-managed wallets through ABI accounts on 15 November 2026. Customers authenticate to ABI with a password or a linked provider; neither Google nor GitHub is required for wallet provisioning. Privy holds the signing keys. ABI authorizes operations through an enabled human account with an active owner membership, CSRF protection and workspace checks. This is application custody, not customer-controlled signing.

## Provisioning and existing addresses

Each workspace presents one wallet, backed by separate Ethereum-compatible Privy wallets for USDC and ETH. The original workspace wallet remains the USDC account; the ETH account is provisioned on demand. A durable, application-specific external ID and request key make creation retryable. ABI retrieves by external ID before creating, recovers an ambiguous creation response, validates the provider binding and verifies a fresh EIP-712 connection signature. The proof cannot authorize a payment. Addresses remain unavailable until verification succeeds. Existing application-controlled trial wallets are adopted with the same address and provider ID. An app or wallet mismatch stops provisioning rather than replacing keys. Earlier customer-owned wallet records remain intact; they are not reassigned to application custody.

Workspace creation attempts provisioning and preserves the workspace if the provider fails. Overview catches up existing owner workspaces after sign-in. A Durable Object alarm also provisions one existing workspace belonging to a verified, enabled account owner per minute; failed attempts wait ten minutes. It never creates customer accounts or synthetic production users. Structured `abi.wallet.provision` events report ready/pending and sanitized failure codes. Privy secrets remain only on the existing API Worker.

The separate earlier organization custody route remains inspectable in Settings under “Historical wallet recovery.” No money, journals or historical custody keys move automatically.

## Currencies and balances

Mainnet ETH and native USDC on Base (8453) and Ethereum (1) are supported. Clearly labeled test ETH/test USDC on Base Sepolia (84532) remain available for faucet checks. USDC and ETH have different receiving addresses within the workspace. Each asset account retains its own address across the supported EVM networks; balances and token contracts are network-specific. This does not provide Bitcoin or Solana addresses.

Currency selection persists on the workspace and updates Overview, the wallet picker, card and Receive. A chain-ID check precedes RPC reads. ETH/native USDC balances are read at a specific block directly, independently of the legacy deposit scanner. A twenty-second cache avoids excess public RPC calls; failed refreshes clear the selected cached balance. Unavailable is never presented as zero. No inferred USD conversion or internal-ledger credit occurs.

Optional server-side RPC bindings: `BASE_MAINNET_RPC_URL`, `ETHEREUM_RPC_URL`, `BASE_SEPOLIA_RPC_URL`. Public defaults work without new secrets. RPC URLs, credentials, provider response bodies and private keys are never returned to clients.

## Reviewed transfers

Send and Allocate prepare an immutable five-minute review containing source, receiving address, asset, network, amount and an execution-fee estimate. Base’s additional L1 data fee is identified separately rather than presented as included in a total-fee ceiling. Allocate resolves another owned workspace's verified provider address on the server. ERC-20 calldata is generated by ABI; clients cannot submit arbitrary calldata, a chain ID, a provider wallet ID or transaction overrides.

The actual token/native balance, ETH for gas, chain, destination and fee are checked before review. Confirmation rechecks the wallet binding, card freeze and treasury policy, including organization freeze, destination block/allowlists and USDC withdrawal limits. Existing enabled MFA protects confirmation. USDC transfers above the treasury review threshold and any transfers requiring a multi-guardian quorum remain blocked until that approval workflow is integrated; they cannot bypass review. Native ETH follows the existing native-asset policy semantics; USDC-denominated caps are not an ETH/USD quote.

A SQLite transaction claims a durable per-workspace/network lock before submitting. Repeated confirmation returns the recorded outcome. A provider timeout or missing response becomes unknown and keeps the lock; it never becomes a claimed failure that invites a duplicate send. Submitted transactions remain pending until a verified receipt has two additional blocks. Reverted transactions are shown as reverted. The UI polls pending transaction status and links to the network explorer. Mainnet transfers are never broadcast by a test or a deployment check.

Operators must reconcile an unknown submission in Privy using its persisted request/reference ID and verify its chain outcome before changing the lock. No automatic resend or fund migration is allowed.

## Agent payments and credits

Mainnet receiving/owner transfers do not activate mainnet agent settlement. Existing x402 signing, agent allowances, reservations and journals still use the deployed Base Sepolia rails. The API explicitly returns `spendingEnabled: false` for these new Privy wallets, and the UI separates the agent allowance. Connecting Privy to x402 requires network-specific signer routing, reservations, receipt reconciliation and recovery testing before cutover. Card-funded USD credits remain separate.

## Mainnet Add money flow

The workspace's **Add money** button and the card's currency dialog use the same verified managed-wallet binding. Open **Assets**, then choose a currency from the **Base Mainnet** or **Ethereum Mainnet** group. Supported real deposits are native USDC and ETH on Base mainnet or Ethereum mainnet. Switching assets selects the corresponding verified account; first use of ETH provisions its dedicated account. Switching networks preserves the selected asset account address. Original addresses are not replaced or swept. Bitcoin, USDT, DAI and other tokens are not enabled by these instructions.

Add money starts on mainnet even if the last selection was a test asset. Faucet networks require the explicit **Show test networks** option. ETH on Ethereum Sepolia is not supported by this catalog and will not appear as Base Sepolia ETH. Send on the exact displayed network; native USDC differs from bridged USDC/USDC.e.

While the funding dialog is open and the page is visible, the selected balance refreshes every 25 seconds, respecting the API's 20-second cache. A manual refresh remains available. The displayed observation time is a balance check, not proof of a particular incoming transaction or its finality. Refresh failures remain unavailable rather than becoming zero.

The legacy account address is removed from workspace funding. Owners can inspect its address, network and on-chain balances under **Settings → Historical wallet recovery**, with explicit instructions to use Add money for new deposits. This section has no receiving or copy-address action. Existing deposits stay at their original addresses; no funds are migrated.

Mainnet receiving and reviewed owner withdrawals already exist independently of the testnet agent settlement rail. These UI changes do not activate mainnet agent spending, convert ETH to stablecoins, or credit the separate card/agent ledger. Verify the signed-in workspace's actual provider address, deposit visibility and withdrawal path before describing mainnet funding as proven end to end. Automated fixtures do not move real funds.

## Separate addresses per asset

The original `abi_managed_wallets` binding is retained unchanged as the USDC account and workspace selection record. ETH has a separate binding in the additive `abi_managed_asset_wallets` table, keyed by workspace and symbol, with a stable external ID and durable request key. The same provider validation, signature proof, app binding and owner checks apply. SQL uniqueness plus an atomic cross-table check prohibits an ETH account from reusing a USDC address or provider wallet. Failed setup never falls back to the other asset’s address. The additive table is installed by the shared SQLite schema on Node and Workers; no customer funds or keys are migrated.

Send resolves its source by the requested asset; Allocate also resolves the destination by that asset rather than the destination's currently displayed selection. Confirmation resolves the persisted provider wallet ID against known workspace accounts, preserving prepared reviews and historical ETH transfers from the original address. It rechecks the immutable source address and the existing freeze, MFA and treasury rules. The existing per-workspace/network pending lock remains deliberately conservative across both accounts.

ETH previously sent to the original shared workspace address remains there. Owners can open **Settings → Recover assets at an earlier workspace address**, choose **USDC account · original workspace address**, and review an ETH transfer from that address. This uses a server-validated account selector, never a client-supplied provider wallet ID or arbitrary transaction data. Recovery can also inspect/send supported tokens received at the other known account. Balance caches always match the source address; recovery reads do not replace the normal asset-to-address mapping. No automatic resend, sweep or conversion occurs.

USDC sends require gas ETH at the USDC account's address on the same network. ETH at the distinct ETH account cannot pay its fees. The funding and sending dialogs state this explicitly, and the send preflight checks the actual source address's gas.

Deploy the API before enabling separate asset addresses. The frontend accepts older verified responses without `accountSymbol`, labels the shared-address model accurately and keeps existing receive/send available. Per-account recovery requires an explicit matching `accountSymbol` and requested asset; it is unavailable on older APIs. Invalid metadata still fails validation and is shown as a readable error rather than a raw schema exception. The catalog remains ETH and native USDC only. Adding further stablecoins or non-EVM networks requires provider routing, official token contracts, decimal handling, gas handling and transfer policy integration; visibility in Privy alone does not establish support.
